# 案例设计说明

`catalog.json` 是自动化案例的业务索引，不是“已通过”清单。每个案例必须在真实页面和真实API 上执行后，才可以把状态从 `DESIGNED` 或 `PARTIAL` 提升为 `PASS`。

## 案例编号

| 前缀         | 业务域                               |
| ------------ | ------------------------------------ |
| `SMOKE`      | 登录、工作台、菜单和健康             |
| `INIT`       | `/systemInit`、首轮预置和设置归属    |
| `ERP-SALES`  | CRM 合同、销售订单、应收收款和履约   |
| `PROC`       | MRP、请购、采购、到货和应付          |
| `MES-PROD`   | 生产、排产、领料、报工、安灯和过程检 |
| `WMS-QC`     | WMS 实物、ATP、质检和库存守恒        |
| `FMS`        | outbox、inbox、草稿、确认和过账边界  |
| `PLM`        | 项目、产品、BOM、工艺和正式发布      |
| `IOT`        | IoT 产品、设备、分组、遥测和告警     |
| `INT`        | 集成平台、实例、映射和同步任务       |
| `HRM/PMS/OA` | 人力、项目协作和 OA/BPM              |

## 每个案例的最小实现

后续 AI 为案例补实现时，必须在 `suites/<suite>.mjs` 中使用 `runCase({ caseId, ... })`，并完成以下层级：

1. `CONFIG`：读取真实初始化/设置页，记录已有配置，判断是否需要补入初始化流程。
2. `UI`：从菜单或真实路由进入页面，完成新增、提交、审核、弃审、作废、红冲等动作。
3. `API`：核对业务 `code`、关键 ID、状态、错误信息和幂等结果。
4. `DB`：使用只读 SQL 核对主表、明细、事实源、数量/金额和租户。
5. `EVENT`：核对 outbox、inbox、BPM、通知、回写和重试/死信。
6. `REVERSE`：执行该案例定义的反向动作，确认不重复扣减、不覆盖其他字段。
7. `EVIDENCE`：保存截图、trace、API 摘要、数据库摘要和测试数据编号。

## 不能替代的断言

- WMS 余额不能用 ERP 或 MES 表替代 `mes_stk_inventory`。
- 库存会计金额不能用 WMS 成本字段替代 ERP 受控成本快照。
- FMS 草稿不能当成正式过账，确认不能当成过账。
- 合同“创建成功”不能代替“审批通过 + 确认签署”。
- 质检页面有数据不能代替物料配置触发和不合格阻断。
- Job 生成数据不能代替真实页面业务链，Job 默认保持关闭。
- HTTP `200`、页面打开、列表有行都不能单独构成 `PASS`。

## 新增配置项的判断

测试发现下拉框为空或流程被配置阻断时，先回查当前模块已有系统配置、业务配置和字典。满足以下条件的配置进入 `/systemInit`：

- 缺失会阻断已选模块建档或出单；
- 可以由平台标准模板安全补缺；
- 多条业务链共同依赖；
- 需要首轮物化到当前租户。

只适合企业运行后维护、依赖真实资产/凭据/会计主体或外部编码的配置进入设置，不新增配置表。初始化页和设置页必须复用同一 Service/API。
